# CI modernization and resource fit

Execute the current [shared CI standard](https://github.com/mykcs/.agents/blob/main/docs/agents/CI_STANDARD.md),
the [Passport contract](https://github.com/mykcs/.agents/blob/main/docs/agents/CI_PASSPORT_TEMPLATE.md)
and each project's local owners. This reference owns the inspection/repair sequence, not CI policy,
vendor assignments, prices or permanent balances. Read a verified current checkout or fetch the
canonical remote document when installed home directories do not contain those docs.

## Desired outcome

Modern, elegant, simple CI fits the user's actual workloads and resources. Prefer the smallest
sufficient topology, repository-owned validation, clear authority and useful feedback. A newer
provider or zero advertised price alone is not an improvement. Keeping healthy CI, CI_NONE and
simple DEPLOY_ONLY are valid outcomes.

## 1. Establish scope and current responsibility

Read project Agent/Dev/CI owners, configuration, validators and effective live rules. Map Source,
CI, Preview, Production, Runtime and Product identity before comparing tools. Reuse the current
registry and accepted scope; lifecycle and maintenance-effort limits matter. Archives need no
symmetry-driven CI. A requested old-repository effort cap does not apply to its active sibling.

Inspect related open PRs/writers and recent material changes. Use existing verified evidence and
bounded incremental reads; do not rescan every historical log or repeat expensive acceptance
without a changed candidate, invalidated contract or unresolved question. Completed rollout
receipts are provenance, not current instructions.

## 2. Diagnose the consumed resource

Separate scheduler/check reporting from runner compute; distinguish trigger, queue, bootstrap,
checkout, validator, reporting and deployment failures. A private hosted-minute outage is not a
code failure, nor proof that the scheduler must move. A deployment provider's capacity is not a
generic CI allowance. Keep provider/product/account meters separate.

Use a small evidence row in the existing work record when useful:

`project/owner → role/product/meter → current eligibility/capacity → observed pressure → decision/proof`

Resolve the billed repository owner/account, public/private access, runner type, reset/overage
behavior, storage/cache/artifacts, concurrency and timeout when they affect the choice. Check
current official documentation and the authorized account UI/API. Published plan eligibility is
different from actual account entitlement or remaining balance. Mark unavailable values unknown;
report measured trigger/run changes separately from billing savings. No fabricated savings or
complete-billing inventory is required for a safe local waste fix.

## 3. Remove demonstrated waste first

Inspect duplicate push/PR triggers, obsolete runs, dependency/toolchain setup, safe cache keys,
semantic routing, retention, early expensive lanes and tiny push loops. Compare actual before/after
behavior and preserve coverage for every mergeable path. Distinguish cancelling obsolete PR work
from serializing production publication. Use accepted manual recovery where automatic cancellation
is unavailable or unverified; do not claim automatic capability.

Implement understood reversible fixes in the existing owner, reuse validator commands and add
meaningful positive/negative guards for actual regressions. Investigate flaky tests against their
real invariant before changing thresholds. Preserve security, secret/fork isolation and final
acceptance while reducing maintenance. Batch one stable candidate before hosted final validation.

## 4. Qualify an alternative only when needed

If measured pressure or missing capability remains, compare KEEP / optimize / alternate compute /
alternate provider. Include queue/retry time, maintenance, private-repository eligibility, trust,
platform fit and rollback alongside monetary cost. Cloudflare Builds/runtime/Pages, Actions,
Buildkite, CircleCI and Vercel have separate roles and meters; current local authority decides fit.

Before implementation, verify the actual personal/organization account, source checkout/App
access, secret/fork boundary, plan eligibility, limits and overage behavior. A trial is finite.
Interactive Mac contention, persistent-runner maintenance and scientific/GPU responsibilities
are real costs and authority boundaries, even when no hosted invoice appears.

Follow the shared standard's non-authoritative shadow qualification and authority-transfer
contract. Prove checkout, validator parity, failure reporting, check/App identity and rollback.
Keep merge protection effective during transition; retire or explicitly downgrade the predecessor.
Prepare reviewable changes before requesting new access/spending/publication approval. Never
change visibility, extract credentials, purchase capacity or repurpose research compute to get
an advertised free tier.

## 5. Verify actual execution and publication

Use the project's exact head/base/freshness contract, effective required authority and owning
workflow/provider logs. A missing check needs routing/authority diagnosis; it is not PASS. Legal
excluded work is separate from a required final gate that never ran. Read actual applicable task
results and positive included-path evidence instead of manufacturing a skipped event.

Inspect push/merge publication effects before acting and retain already-granted specific approval.
After authorized integration, verify remote main, merge reachability or applicable squash/tree
equivalence, declared/live authority and required main smoke/publication. Tree equivalence does
not waive freshness or claim literal candidate checkout. A deployment Ready/HTTP 200 login page
does not prove intended content; use existing authorized access and artifact-aware acceptance.
For shared native browser surfaces, verify isolation or serialize exclusive navigation and check
URL/repository/SHA before reading evidence. API/CLI reads can remain independent.

## 6. Close with the smallest current projection

Update the existing local CI/Dev owner and any affected registry/auditor expectations. Prefer
stable navigation/invariants over audit markers that freeze a temporary status. Preserve dated
receipts and unknown measurement limits. Re-audit latest integrated state; report inspected
coverage, integrated improvements, justified no-change decisions and concrete remaining boundaries.
