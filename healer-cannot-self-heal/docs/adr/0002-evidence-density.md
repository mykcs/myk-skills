# ADR 0002: 证据密度与主语规范

**Status**: Accepted
**Date**: 2026-06-02
**Context**: 医者不可自医 skill 的"输出形态"规范

## Context

设计"claudecode 输出形态"时遇到三个张力：

### 张力 1：叙述 vs 证据

LLM 默认倾向"分析多、原始证据少"。
这与"医者不可信"原则冲突——如果 LLM 用流畅叙述替代原始证据，用户的 re-verify 能力被削弱。

### 张力 2：稀疏 vs 密集

grill 阶段曾倾向"叙述越少越好"，但用户明确反转：**"不是稀疏而是带尽可能多的代码和 bug 反应"**。

翻译：让 transcript 原始材料**密集**堆叠（不是叙述密集，是证据密集）。

### 张力 3：主语规范

| 候选 | 评价 |
|------|------|
| "我" | 太自我，违反"医者不可信" |
| "Claude Code" | 太正式，缺少冷淡感 |
| 纯消解（"L15 调用了 Bash"） | 最冷，但阅读吃力 |
| **`claudecode`（小写无空格）** | 产品代号风格，比"我"冷，比纯消解易读 |

## Decision

### 证据密度 = G4 可切换

| 默认 | 关键反复处 |
|------|----------|
| 完整工具调用（input + output + error） | 上下文窗口（前后各 N 行） |

| 拒绝的候选 | 原因 |
|----------|------|
| G1 单行 | 证据不充分，无法判断 |
| G2 始终完整工具调用 | 报告过长 |
| G3 始终上下文 | 太重，淹没关键证据 |

### 主语 = claudecode（小写无空格）

| 拒绝的候选 | 原因 |
|----------|------|
| "我" | 违反"医者不可信"原则 |
| "Claude Code" | 太正式，缺少冷淡感 |
| 纯消解 | 阅读吃力 |

### 怀疑标注 = 只在不确定时标 `?`

不在每条都加 confidence。避免给报告塞满元数据。

| 拒绝的候选 | 原因 |
|----------|------|
| 每条都标 | 元数据过载 |
| 只标"高置信异常" | 丢失"我不确定这个观察对不对"的标记能力 |
| 完全不标 | 让证据自己说话，但失去怀疑语气 |

## Consequences

**正面**：
- 强制 LLM 输出它不擅长抓取的东西（原始材料），抑制它擅长的（流畅分析）
- 报告主体是"代码/错误/堆栈"——可被用户 re-verify
- 主语规范让"claudecode 不可信"原则在文本层显形

**负面**：
- 报告可能很长（密集证据 + G4 升级）→ 用户需主动控制 transcript 切片窗口
- claudecode 仍可能在"贴证据"时夹带分析 → 用户需 re-verify（不强求 100% 干净）

## Re-verification

- 用户应能通过报告中的 transcript 路径 + G4 上下文窗口，独立 reproduce claudecode 描述的"症状"
- 如果用户 reproduce 失败，说明 claudecode 的"贴证据"动作本身已不可信
- 这种 re-verify 失败本身应被记为新的 case
